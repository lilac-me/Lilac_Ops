# Doc-Agent 使用指南

Doc-Agent 是面向仓库资料工作的统一入口，支持两类任务：检查已有资料，以及基于仓库事实撰写新资料。它在 Claude Code 和 Codex 中使用同一套编排流程、规则和产物契约。

## 1. 安装、启动与基本用法

### 安装与确认

在 MindSpeed-Agent 仓库根目录执行与目标平台对应的安装命令。安装脚本会安装本仓库面向该平台的插件，其中包含 Doc-Agent；完整说明见 [MindSpeed-Agent 快速开始](../../README.md)。

Windows（CMD）：

```cmd
install.bat codex
install.bat claude-code
install.bat all
```

Linux / macOS：

```bash
bash install.sh codex
bash install.sh claude-code
bash install.sh all
```

只需执行与目标平台对应的一条命令。脚本退出码为 0 且输出 `Doc-Agent installed for Codex` 或 `Doc-Agent installed for Claude Code`，表示安装完成。也可以按平台查询插件状态：

```text
codex plugin list
claude plugin list
```

安装或更新后新建一个会话，再开始资料任务。Codex 可以在编排工作目录执行 `codex .` 后输入请求；Claude Code 直接在会话中输入请求。

### 调用方式

推荐直接用自然语言描述任务。需要显式指定入口时，按平台使用：

```text
# Codex
$doc-orchestrator 检查 <目标仓绝对路径> 的资料

# Claude Code
/doc-agent:doc-orchestrator 检查 <目标仓绝对路径> 的资料
```

`doc-orchestrator` 是唯一公开入口。通常不需要手动指定内部 Agent；编排器会根据请求在上下文收集、资料设计、撰写、审查和修复之间调度。

### 输入信息

建议在请求中明确以下信息：

- 目标仓库的绝对路径或当前工作目录。
- 是“只检查已有资料”还是“撰写新资料”。
- 文档范围，例如全仓库、某个目录或指定文件。
- 目标仓性质：昇腾自研开源仓，或参与业界主流开源社区的三方仓。
- 目标受众、语言、存放位置和是否允许修改目标仓库。
- 工作产物根目录；不指定时使用编排工作目录下的 `.doc-work/`。
- 审查深度：`L0`、`L1` 或 `L2`。

如果目标仓是三方仓，还应说明允许修改的目录或协作方式；无法判定时，编排器应先询问，不会自行假设。复制下文示例时，需要把尖括号中的虚拟路径替换为实际值。

### 审查深度

| 深度 | 检查内容 | 适用场景 |
| --- | --- | --- |
| `L0` | 确定性 lint | 格式、链接、占位符、导航等快速检查 |
| `L1` | lint + 正确性代码审查 + 完整性审查 | 小范围修改、单章更新、常规资料检查 |
| `L2` | lint + 正确性代码、正确性语义、完整性、易理解、易获取五类审查 | 新资料或需要完整评估的资料 |

存量资料通常从 `L0` 或 `L1` 开始；新资料默认使用 `L2`。如果没有可用的 NPU 环境，涉及运行结果的代码块会被标记为需要人工验证，不会被伪装成已通过。

## 2. 已有资料检查

### 2.1 推荐请求方式

只检查、不修改目标仓库：

```text
请使用 doc-orchestrator 检查 `<目标仓绝对路径>` 的中文资料。
重点检查简介、安装指导和快速上手，输出每个问题的文件位置、证据、严重级别和修复建议。
本轮只做检查，不修改目标仓库；审查深度使用 L2。
```

检查全仓库资料组合：

```text
请审查 `<目标仓绝对路径>` 的资料完整性和质量。
按仓库实际能力识别必备资料，逐组检查；只报告问题，不直接修改。
```

如果希望检查后自动修复，应明确写出：

```text
请检查并修复 `<目标仓绝对路径>` 的中文资料。
先给出检查结果，再按问题清单逐轮修复，修复后重新审查；无法验证的问题保留为人工处理项。
```

### 2.2 检查流程

已有资料检查属于存量资料场景，流程如下：

1. 识别目标仓库、中文资料范围和仓库能力。
2. 根据仓库级资料清单识别缺失项，并按主题、对象、术语和文档类型分组。
3. 对每个文档或文档组先运行确定性 lint。
4. 按审查深度决定是否调度 reviewer：`L0` 不调度，`L1` 调度两类，`L2` 调度五类。
5. 汇总问题，生成质量报告。
6. 用户要求修复时，按 `critical → major → minor` 单轮处理并重新审查，最多循环三轮；仍无法闭环的问题进入人工处理清单。

存量检查不需要人工确认 H2 章节清单；只有新资料撰写流程需要这一确认环节。

### 2.3 默认资料范围

Doc-Agent 的资料清单约束的是“仓库需要哪些资料”，不规定每份资料必须采用固定章节。默认必备项包括：

简介、最新消息、版本说明、安装指导、快速上手、支持特性或支持模型、特性开发指导或模型/特性开发指导、安全声明、免责声明、License 声明、贡献声明、FAQ 和致谢。

模型仓库还会按能力检查性能调优指导；提供工具链能力的仓库还可检查工具链使用指导。目录结构、未来规划、加入我们、模型推理和模型评测属于可选资料，可在请求中明确要求纳入或排除。

### 2.4 如何看检查结果

每次任务都在指定的工作产物根目录中创建隔离 run。未指定时，`.doc-work/` 相对于编排工作目录解析：

```text
<编排工作目录>/.doc-work/<repo>/<run-id>/
```

如果编排工作目录就是目标仓库，应在请求中指定一个位于目标仓库之外的工作产物根目录，避免运行产物进入目标仓。多文档任务会为每份文档或每个审查分组创建独立 run。

重点关注以下产物；“新资料”表示仅在新资料撰写流程中产生：

| 产物 | 适用场景 | 用途 |
| --- | --- | --- |
| `run.json` | 全部 | 当前 run 的目标文档和运行标识 |
| `context_report.json` | 新资料 | 仓库形态、能力、资料清单和事实基线 |
| `design_plan.json` | 新资料 | 资料类型、H2 章节清单和插图基线 |
| `design_approval.md` | 新资料 | 用户对章节清单的确认记录 |
| `draft_{doc}.md` | 新资料 | 待审查和交付的文档正文 |
| `figure_requests.json` | 新资料 | 待人工提供的插图需求 |
| `lint_report.json` | 全部 | 确定性检查结果；问题通常包含规则、位置、证据和建议 |
| `review_report.json` | 全部 | 本轮要求的 reviewer、完成情况和文档哈希；`L0` 不要求语义 reviewer |
| `code_verify.json` | `L1/L2` | 代码块逐块验证结果；无环境时可能是 `manual` |
| `quality_report.json` | 全部 | 汇总后的分数、维度结果、结论和当前问题 |
| `issues.jsonl` | 语义审查与修复 | 语义问题的追加式生命周期记录 |
| `ledger.jsonl` | 全部 | 状态机阶段和 handoff 记录 |

`quality_report.json` 的 `verdict` 只有三种：`pass`、`fail` 和 `manual_intervention`。生成 `pass` 前，lint、必需 reviewer 和文档版本哈希必须满足契约；`L1/L2` 还要求 `code_verify.json` 中全部代码块为 `pass`，`L0` 不要求代码验证。`fail` 时优先按报告中的 `rule_id`、文件位置和证据定位；`manual_intervention` 表示仍有无法自动闭环或需要人工验证的事项，不应当作通过。

编排器输出的 `handoff: NEED_FIX` 和 `handoff: MANUAL_INTERVENTION` 是状态机控制消息，不是 `quality_report.json` 的字段值。

### 2.5 检查范围说明

- `docs/en/**` 由翻译团队负责，不作为本流程的中文资料检查范围。
- 昇腾自研开源仓按适用规则检查中文资料是否位于 `docs/zh/`；三方仓不应用该存放规则。
- 三方仓需要明确协作方式和修改边界：只在约定目录内修改，或仅输出对上游共享文件的修改建议。目标仓性质和边界不应由工具臆测。

## 3. 新资料撰写

### 3.1 推荐请求方式

```text
请基于 `<目标仓绝对路径>` 撰写一份中文“快速上手”资料。
目标读者是第一次使用该项目的开发者，内容必须以仓库中的脚本、配置和代码为依据，
覆盖环境准备、安装、最小运行示例、结果确认、常见失败处理和下一步入口。
请先完成资料设计并展示 H2 章节清单，等我确认后再写正文；写完按 L2 审查。
```

如果需要一次补齐多类资料，可以这样描述：

```text
请基于 `<目标仓绝对路径>` 设计并撰写简介、安装指导和快速上手三份中文资料。
先识别仓库事实和资料组合，分别给出每份资料的 H2 清单供我确认；确认后逐篇撰写、审查并报告遗留问题。
```

### 3.2 撰写流程

新资料场景按以下顺序推进：

1. **上下文收集**：读取仓库代码、脚本、配置、已有入口和相关记录，形成共享事实基线。
2. **资料设计**：确定资料类型、目标读者、必选/可选 H2 章节和插图基线。
3. **人工确认**：编排器展示 H2 章节清单；你可以确认，或提出增删和调整意见。未确认前不会进入正文撰写。
4. **逐章撰写**：按确认后的章节从目标仓库取证，不凭空补写版本、命令、结果或路径。
5. **质量审查**：默认按 `L2` 执行 lint 和五类 reviewer 审查。
6. **修复与复查**：用户允许修改时，根据问题清单单轮修复，再回到审查阶段；最多三轮，剩余问题明确列出。
7. **收尾交付**：给出正文路径、质量报告、插图需求和遗留问题。

### 3.3 写作时需要特别说明的事项

- 命令应能复制执行；`<...>` 形式的占位符必须替换为实际值，或明确说明如何取得实际值。
- 代码注释属于资料内容，不能因为是注释就删除；错误注释需要依据代码行为修正。
- 无法在当前环境验证的命令或版本要标记“需实测验证”，不能编造成功结果。
- 插图只登记需求并在正文放置统一占位符，不自动生成或伪造截图。插图清单位于 `figure_requests.json`。
- 同仓链接优先使用相对路径；新文档需要补充仓库 README 的可达入口。
- 如果目标是昇腾自研开源仓，中文资料的存放位置需遵循仓库适用的 `docs/zh/` 规则；具体以审查结果为准。

### 3.4 设计确认时看什么

确认编排器展示的 H2 章节清单时，重点检查：

- 资料是否覆盖真实使用路径，而不是只罗列概念。
- H2 顺序是否符合目标读者的阅读和操作顺序。
- 安装、最小示例、成功标志、失败处理和下一步入口是否齐全。
- 每个章节是否有可取证的信息源。
- 可选章节是否确实需要，是否会造成重复或维护负担。
- 插图是否有明确用途、元素和替代文本。

只需用自然语言回复“确认该章节清单”；不需要查看或编辑 `design_plan.json`。需要调整时，直接说明要新增、删除或改名的章节及原因。

## 4. 常见问题处理

### 任务停在某个阶段

用“请查询当前 doc-agent 运行状态并从断点继续”恢复。编排器会读取当前 run 的账本，不需要重新创建整个任务。源码调试或需要手动核对时，可使用：

```text
python "<DOC_AGENT_ROOT>/engine/state_machine.py" current --workspace "<run-workspace>" --yaml "<DOC_AGENT_ROOT>/engine/doc_pipeline.yaml"
```

该单行形式可用于 Bash、PowerShell 和 CMD。其中 `<DOC_AGENT_ROOT>` 必须解析为当前安装的插件根目录，不能硬编码 Codex 缓存路径。

### 报告显示没有通过结论

先区分三类情况：

1. `lint_report.json` 失败：先修复路径、链接、占位符、导航或资料清单问题。
2. `review_report.json` 不完整：说明必需 reviewer 没有完成，不能评分。
3. `code_verify.json` 出现 `manual` 或 `fail`：需要提供可用运行环境、补充证据或人工确认；不能直接发送通过结论。

### 想只看某一份资料

在请求中给出目标文件的仓库相对路径，并说明是否连带检查 README 导航、交叉引用和资料清单。例如：

```text
只检查 docs/zh/quickstart.md，并检查 README 到它的入口是否可达；不要检查其他文档，也不要修改文件。
```
