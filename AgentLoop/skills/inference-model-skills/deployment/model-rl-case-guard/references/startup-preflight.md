# 最终启动环境与阶段进度

在启动大模型前执行本检查。复用 `vllm-ascend-serving` 的连接、启动和状态入口；
本参考补充需验证的条件，不假定现有 `serve_start.py` 已自动完成以下全部检查。
SSH 和模型目录存在只是预检的一部分。

## 1. 在实际服务环境检查

检查每个节点将要使用的容器/Conda 环境，以及 CANN setup、环境变量覆盖、worker 覆盖项和 wrapper。
预检命令应在相同上下文中执行；wrapper 不能复用于预检时，保留它的环境变更，在服务启动后核对实际进程。
只预检 head，或只在宿主机新 shell 中成功 import，不代表所有 worker 可以运行。

逐节点归档以下证据到 `logs/startup-preflight.json`，保留检查命令和日志路径：

| 检查 | 记录与通过依据 |
| --- | --- |
| 执行身份 | 节点、容器 ID/镜像 ID 或 Conda 环境、实际 cwd、选定设备、配置版本/哈希 |
| Python 与入口 | `command -v vllm`、实际 Python 可执行路径、torch/torch-npu/vLLM/vLLM-Ascend 版本与模块路径；排除 cwd 中同名源码遮蔽已安装包 |
| CANN 与动态库 | 实际 source 的 setup 路径、CANN 版本、PATH 与必要的库搜索路径；在同一环境 import torch、torch_npu、vllm，保留原始加载错误 |
| 编译工具 | 按当前实现所需工具检查 `command -v`、实际可执行路径和版本；不能因动态库可加载就判定编译工具也可用 |
| Triton 后端 | 仅在当前模型/后端使用 Triton 时，核对部署版本实际的后端注册、工具路径及目标支持；不依赖其他版本的固定内部 API |
| 节点一致性 | 比较模型配置/权重索引身份、关键依赖和修复文件版本；明确差异是否兼容，不能把 head 的检查结果复制给 worker |

只保存必要环境白名单：Python/CANN/PATH/库路径、设备选择和通信变量等。
不要执行完整 `env` 转储或保存可能含凭据的变量、连接 URL 和命令参数。

注意环境覆盖顺序：CANN setup 成功后，`--extra-env PATH=...` 或 wrapper 仍可能覆盖编译工具路径。
需要补 PATH 时保留当前 Python 和 CANN 的必要目录，不用某台机器的硬编码路径替换全局环境。
检查失败时仅修改本任务启动配置并重新验证受影响节点，不能改其他容器或宿主全局配置。

### Triton 路径验证

静态 import/后端注册只能确认元数据，不证明内核可在设备运行。
若目标版本已有合适的小型 kernel 用例，可在已授权且空闲的本任务设备上验证编译/执行；
保存脚本版本、命令、节点、设备和结果。不为预检加载全量模型，也不自动引入新的模型专项探针。
缺少设备或目标用例时记录运行验证 `not_run`；必要的编译器或后端缺失则记录依赖 `blocked`。
后续真实调用成功才可作为相应执行路径通过的证据。

## 2. 核实实际通信接口

多机场景检查最终生效的 `HCCL_IF_IP`、`GLOO_SOCKET_IFNAME`、`HCCL_SOCKET_IFNAME`、
`IP_SOCKET_IFNAME` 及当前后端额外使用的变量。检查对象是应用所有覆盖项后的服务进程环境，
不是启动脚本打印的默认 NIC 名称。

- 在服务所在网络命名空间核对接口存在、链路状态、本机地址和到 peer 数据地址的路由。
- 结合宿主/容器网络模式核对 HCCL 地址绑定规则；显式通信 IP 应符合目标平台约束。
- 记录可取得的链路速率及来源，区分管理网与数据网；虚拟接口速率未知时记录未知，不能推定为高速链路。
- SSH 或 API 可达只证明相应通道，不证明 HCCL/Gloo 数据面正确；已有通信压测可复用，但需记录真实绑定接口和拓扑。
- 接口名称和 IP 不写死为某种 A5 机型的通用规则。平台默认 NIC 与实机不符时，先核对目标版本的显式覆盖方式，再在所有节点配置并复查，不擅自改路由、防火墙或系统网卡设置。

可使用 `ip -j addr`、指定 peer 的 `ip route get` 和可用的链路信息工具作只读检查；
路由探测须使用当前绑定方式，默认路由不能代替带接口/源地址约束的结果。
一旦服务启动，还需核对最终通信变量和日志中的绑定地址。仅采集本任务进程的必要环境字段。

任一必要节点未检查、必要接口无效或必需依赖缺失，保留节点级原因并停止进入下一阶段；
容量、资源占用和容器归属仍按主流程检查，环境检查不能代替可用卡确认。

## 3. 记录启动阶段并设置有界等待

启动前记录配置中的 `--dp-rpc-timeout`、`--health-timeout`，以及目标引擎版本实际支持的内部就绪等待项。
这些计时器可能嵌套或重叠，调大外层不能自动延长内层；不能套用另一版本的环境变量名称。
预算依据权重规模、既有加载/编译记录和用户机时确定，不统一写死为 600s 或 3600s。

按节点持续读取本任务完整服务日志，保存原始行或文件位置、时间和最近进展。
可在 `logs/startup-progress.json` 中记录各阶段 `state`、`started_at`、`last_progress_at`、
`elapsed_seconds`、适用预算及证据路径；未观测到阶段标记时写未知，不能猜测完成。

| 阶段 | 可用证据与处理 |
| --- | --- |
| 权重加载 | 分片进度、加载耗时、进程存活及首个异常；加载仍在推进时不能仅因 API 暂不可达判失败 |
| 通信初始化 | head DP RPC 监听、worker 加入和 HCCL/Gloo 日志；端口监听不等于所有通信组建立成功 |
| 编译/图捕获 | 编译任务或 graph capture 日志及进展；与加载阶段分别记录 |
| 服务就绪 | head `/health`、`/v1/models` 与各 worker 状态；再运行既定基础推理探针，不能只看 API 进程存在 |

以上是观测分类，不假定所有版本均按此顺序串行执行；加载、通信和编译可能交错。
继续使用 serving 入口规定的 DP 启动顺序，不另写阶段驱动或 SSH 重试循环。

- API 尚未就绪但日志有进展：在预先记录的预算内继续观察，报告当前阶段和最近进展。
- 进程退出、出现致命异常或任一适用等待预算到期：保留全部节点的首个错误、阶段和已用时间，进入现有失败诊断与清理流程，不无限延长等待或自动循环重启。
- 无日志进展时报告未知/疑似停滞并检查进程、通信和编译状态；不能把日志沉默直接判为死锁。
- 调整超时、wrapper、PATH 或通信配置后，记录差异并重新预检；清理仅针对已核实属于本任务的进程/服务。

在最终报告中分别说明静态预检、真实 kernel 探针、集群就绪与模型请求是否通过。
本参考只增强开箱检查，不改变目标模型、特性参数或精度验收合同。
