## 输入要求

### 最小输入

至少需要以下一种：

- 模型配置文件；
- 模型主实现文件；
- 可访问的模型代码仓；
- 用户提供的结构参数表。

### 推荐输入

| 输入 | 用途 |
| --- | --- |
| `config.json` 或配置类 | 获取模型结构参数 |
| `modeling_*.py` | 确认真实前向路径 |
| 自定义 Kernel 源码 | 判断算子和 FLOPs |
| 训练启动参数 | 推导训练 FLOPs 和 MFU |
| 硬件型号与精度 | 确认理论峰值 |

### 批量分析清单

```yaml
models:
  - name: model_a
    source: https://repository/model_a
    revision: main
    config: config.json
    modeling: modeling_model_a.py
    target_backend: ascend_npu
    target_precision: bf16

  - name: model_b
    source: https://repository/model_b
    revision: commit_id
    target_backend: ascend_npu
    target_precision: fp8
```

每个模型必须独立记录源码版本，不能把不同 Commit 的配置和实现混用。

## 证据与事实优先级

分析必须遵循以下优先级：

1. 当前用户提供的实际源码；
2. 当前源码对应的配置文件；
3. 当前 Commit 的算子实现；
4. 官方模型报告和官方仓库；
5. 官方框架文档；
6. 论文；
7. 第三方分析文章。

如果配置、文档与源码不一致，以**实际执行源码**为准，并显式列出差异。

禁止：

- 只根据模型名称推测结构；
- 只读取 `config.json` 而不检查 `forward()`；
- 将推理实现直接当作训练实现；
- 将 Buffer 计入可训练参数；
- 将 Total Parameter 当作 MoE Active Parameter；
- 将理论模型 FLOPs 与 Profiler 硬件 FLOPs 混为一谈。

### 可复现基线与证据边界

每次分析必须先建立可复现基线，至少记录：

| 字段 | 要求 |
| --- | --- |
| Repository | 完整公开仓库 URL 或用户提供的本地源码路径 |
| Revision | 完整 Commit Hash、Tag 或不可变版本；不得只写 `main` |
| Analysis Date | 分析日期与时区 |
| Primary Files | 实际读取的配置、模型入口、Kernel、训练/推理入口和权重索引 |
| Config Variants | 区分根配置、推理配置、训练配置和部署配置 |
| Checkpoint Manifest | 若公开，记录分片数、Tensor 条目数、物理字节数和量化格式 |
| Validation Environment | 记录是否具备框架、权重、GPU/NPU、Profiler 和分布式环境 |

执行规则：

1. 优先使用 Commit 固定链接作为报告引用，分支链接只能作为导航；
2. 配置、论文、Checkpoint 和执行源码不一致时，输出差异表，不得静默选择其中一个；
3. 用户要求“从零重做”时，不读取旧报告中的参数、Shape、NPU 或 FLOPs 结论，只允许复用输出 Schema；
4. 每个关键结论使用 `已确认`、`推导`、`合理推测`、`未确认` 中的一种状态；
5. 将“当前源码原样路径”“当前源码的 Eager Fallback”“外部框架的等价实现”作为三个独立证据域；
6. 外部框架已验证不能提升当前源码原样路径的状态，只能作为替代路径单列；
7. 没有运行权重、GPU/NPU 或 Profiler 时，摘要和验收区必须显式声明，不得使用“已验证可运行”等措辞。

## 总体执行流程

```text
源码与配置盘点
    ↓
建立模块调用图
    ↓
模型结构与参数量分析
    ↓
逐模块前向 Shape 推导
    ↓
运行时 Shape 校验
    ↓
非 Eager/自定义算子扫描
    ↓
NPU 支持矩阵与风险分级
    ↓
逐模块 FLOPs 推导
    ↓
整网 FLOPs 与 MFU 公式
    ↓
一致性检查与报告输出
```

---

## 失败与信息不足处理

当源码或信息不足时，不得自行补全。

使用以下状态：

```text
已确认：源码直接支持
推导：根据已确认 Shape 和公式计算
合理推测：有实现依据但缺少运行验证
未确认：缺少源码、配置或算子实现
外部验证：不同框架或独立实现已公开验证，不代表当前源码原样通过
```

报告中必须单独列出：

| 未确认项 | 缺少信息 | 对结果影响 | 建议补充材料 |
| --- | --- | --- | --- |

如果自定义 Kernel 不可见：

- 不得声称其 FLOPs 或 NPU 支持已确认；
- 可给出接口级上界/下界；
- 必须标注“Kernel 内部实现未知”。

---

## 输出风格要求

- 使用专业、准确、可复核的表达；
- 先给结论，再给推导；
- 表格优先；
- Shape 使用统一符号；
- 公式必须说明变量；
- 不使用含糊的“差不多”“应该是”；
- 推测必须显式标注；
- 不只描述模块名称，要解释数据如何流动；
- 不只判断 NPU 支持或不支持，要给出证据和验证方案；
- 不只给最终 MFU，要展示分子和分母如何构成。

---

## 执行指令

收到模型分析任务后，按以下顺序执行：

1. 建立源码和版本清单；
2. 锁定不可变 Revision、配置变体、Checkpoint Manifest 和验证环境；
3. 读取配置和模型入口；
4. 展开真实层类型并分离主模型与附件；
5. 建立模块调用关系；
6. 建立逻辑参数、Active 参数和物理 Checkpoint 三套账本；
7. 提炼结构创新；
8. 推导整网和复杂模块 Shape；
9. 使用小规模实例解释 Mask、TopK、Cache 和路由；
10. 完成 Shape 最低静态验证集或运行时验证；
11. 扫描全部非 Eager、自定义 Kernel 和分布式调用；
12. 分离原始源码、Fallback 和外部实现，建立 NPU 支持矩阵；
13. 从实际 Tensor Shape 推导执行 FLOPs 与算法有效 FLOPs；
14. 组合整网训练 FLOPs 并完成交叉校验；
15. 给出 MFU 公式和代入方式；
16. 按固定 Schema 输出单个 Markdown 报告和结构化 JSON；
17. 执行四项人工验收和最终机器验收。

任何情况下，不得因为模型复杂而跳过四项核心工作。若时间或材料不足，应输出已完成部分、未确认项和继续分析所需的具体输入。
